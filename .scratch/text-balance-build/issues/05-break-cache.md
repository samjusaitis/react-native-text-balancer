# 05: Break cache

Spec: [spec.md](../../text-balance/spec.md) (Break cache). Detail: ticket 14 in [the map](../../text-balance/map.md).

**What to build:** repeated layouts of the same balanced text reuse the earlier balanced breaks. Drawing on the main thread and hit-testing cost almost nothing, while the lines stay identical.

- An `NSCache` (count limit 256) inside the hook.
- **Key:** RN's input attributed string (compared for equality, so string, fonts and paragraph style), width, max lines, `adjustsFontSizeToFit`, and height when `adjustsFontSizeToFit` is on. Don't hash a collection by count.
- **Value:** per paragraph, the balanced line widths and side or "stock", plus the ranges whose `pushOut` was cleared, so that a hit clears them again.
- There's no explicit invalidation. Dynamic Type changes fonts, and therefore the key.

**Blocked by:** 03, 04.

**Status:** done

- [x] Every test-screen sample shows the same result and the same lines with the cache on and off.
- [x] In a Release build, cache hits cost about 0.005ms, and the mean balancing overhead per build drops to roughly a third of uncached (measured 0.42×; see Comments).
- [x] Changing Dynamic Type rebalances balanced text correctly.

## Comments

- **Implementation:** `ios/RNTextBalancer.mm` holds the cache: an `NSCache` (`countLimit` 256) keyed by `RNTBBreakCacheKey` (a copy of RN's input attributed string compared with `isEqualToAttributedString:`, width, `maximumNumberOfLines`, `adjustsFontSizeToFit`, and height only when that's on; hashed on string hash, width and max lines). `RNTBBalanceTextStorage` now returns `RNTBBalancedBreaks`, what it applied: the width container's line widths and sides keyed by line start, plus the paragraph style runs whose `pushOut` it cleared (`RNTBBalancedBreaks.stock` when nothing balanced). On a hit, `RNTBApplyBalancedBreaks` clears `pushOut` on those runs and swaps in a width container with RN's configuration and the cached lines, with no choosing or checking.
- **Height, beyond the spec:** height isn't in the key (except with `adjustsFontSizeToFit`), but it can change the outcome: a container too short for the balanced lines cuts them off, so the check fails and the text falls back to stock. So the value records `minimumHeight` (the bottom of its last line fragment; 0 for stock), and a shorter container counts as a miss. An outcome computed while RN's height cut lines off isn't cached at all. Measure (unbounded height) and draw (the measured frame) still share entries.
- **Same lines, cache on and off** (Release, temporary instrumentation, removed): each hit also rebuilt the same stack uncached and compared every line fragment's character range, rect and used rect, plus the `lineBreakStrategy` runs. 0 mismatches over 181 hits, at the default text size and after a Dynamic Type change. The test screen's per-sample results (badges and detail numbers, logged through a temporary `console.error`) were identical with the cache on and off: 46/46 at the default size.
- **Timing (Release, iOS 27.2 simulator, time in the hook after RN's build, 3 launches each, 70 builds per launch):** hits median 0.005–0.007ms, mean 0.010ms; 46 of 70 builds hit (the test screen's draw and repeat builds). Mean overhead per build 0.41ms uncached → 0.17ms cached (0.42×; the prototype measured 0.68 → 0.25, 0.37×). Key construction and lookup cost 0.002ms per miss, so the rest of the gap is that misses are each string's first, colder build (miss mean 0.47ms against 0.41ms for all uncached builds).
- **Dynamic Type:** switching the running app from Large to XXL (`simctl ui content_size`) missed once per balanced sample (new fonts, new keys) and rebalanced, then hit as before; 0 mismatches. At XXL the test screen shows 41/46 with the cache on *and* off, with identical per-sample results. The five ❌ aren't the cache: `numberOfLines 3, fits` truncates at XXL, so stock is right; Japanese, Chinese and Thai stay at stock-equal widths; and `latin-no-fixed-width` balances to a higher width variance (337 → 370). Those samples' expectations assume the default text size; the last one may be worth a look.
- **Verification gotcha:** a plain `xcodebuild` Debug build loads the bundle from port 8081 (another project's Metro here). Pass `RCT_METRO_PORT=8100`, as `expo run:ios --port 8100` does, or use a Release build, which bundles the current JS.
- **XXL diagnosis (the five ❌ at `content_size extra-extra-large`): no balancer bug.** Release build, temporary native and JS logging (removed): for every build of each sample, the paragraph's stock lines, the balanced breaks `chooseBreaks` chose, and any check-loop mismatch or truncation; plus each sample's stock and balanced line texts. The box is 240pt in every build (`maxWidth` isn't involved), and no sample had a mismatch or fell back.
  - `latin-no-fixed-width`: correct; the expectation only holds at Large. Stock is 5 lines, and its last line ("headline balances", 229.8pt) is already the widest and can't take another word. So stock's split is the only 5-line split, and `chooseBreaks` returns stock's line starts [0 16 30 46 62]. The variance rises (337 → 370) because of how the widths are measured, not because the lines changed. `onTextLayout` line widths include the trailing space. On a balanced line, the fragment is narrowed to the line's text width plus slack (at most 4pt), so most of the space is clipped. Each line but the last reports 2.47pt narrower (a space of about 6.5pt, minus 4pt of slack), while the last line is unchanged. The spread of widths grows, and the line texts are identical.
  - `japanese`: correct, stock is already balanced. At XXL a line holds 10 characters (234pt). 69 characters make 7 lines of 10,10,10,10,10,10,9, the most even 7-line split there is. The balanced breaks equal stock's, and kinsoku holds.
  - `chinese`: correct, same reason. 39 characters at 10 per line make 10,10,10,9.
  - `thai`: correct, stock is already balanced. The paragraph is 917.7pt of text in U = 240, so 4 lines average 229pt, and stock's lines (229.5, 231.5, 225.6, 231.1) leave no room to even out. The balanced breaks equal stock's [0 19 42 62].
  - `number-of-lines-fits`: correct. At XXL the unclamped text is 4 lines, more than `numberOfLines 3`, so it truncates, and the stock wrapping and ellipsis are by design.
  - **One false pass at XXL:** `adjusts-font-size` shows ✅ with line texts identical to stock's. Its first line reports 236.61 → 236.27pt because of the same trailing-space clipping. At Large, the only samples whose balanced lines match stock's are the four that expect stock, so every balanced ✅ at Large comes from moved breaks.
  - **Proposals:**
    1. *Test screen robust to text size:* pass `allowFontScaling={false}` to all three renderings of each sample, because the samples are tuned at Large and every Dynamic Type size changes how they wrap. `maxFontSizeMultiplier` isn't enough, because smaller sizes change the wrapping too. Check Dynamic Type rebalancing (this ticket's criterion) separately, for example with one sample left scalable and checked by eye.
    2. *Tighter `balanced` check:* also require at least one line's text to differ from stock's (the breaks moved), with detail "same breaks as stock" when they don't. Then trailing-space clipping alone can't pass a sample.
    Proposals 1 and 2 are built, along with a script that sweeps every text size (branch `claude/angry-cartwright-9bda37`, see ticket 01's comments). It passes 52/52 at all 12 sizes with this ticket's cache.
    3. *Optional balancer change:* a paragraph whose balanced breaks equal its stock line starts stays on stock wrapping, with no line widths. The output, including `onTextLayout` widths, is then exactly stock's, and the impose-and-check layout is skipped when nothing in the storage changes. It's a small change to the choosing loop in `RNTBBalanceTextStorage`, plus a line in the spec.
