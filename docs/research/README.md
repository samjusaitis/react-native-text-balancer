# Research and prototypes

How the design was reached, in November 2026, before the library was built. The research notes here are kept as written: they describe the options as they stood at the time, including some that were later dropped. What shipped is recorded in the [ADRs](../adr/), and how it works today is in [how it works](../how-it-works.md).

All measurements below are from RN 0.88.1 on an iOS 27.2 simulator.

## Research notes

Each one was read-only research against primary sources (Apple docs and SDK headers, React Native source). Nothing in them was run, so their claims about TextKit behaviour were checked by the prototypes that followed.

- **[iOS native balancing](ios-native-balancing.md):** iOS has no public API that balances lines. The nearest is `NSLineBreakStrategy.pushOut`, which only avoids a lone last word. Every React Native iOS text path (measure, draw, hit-test, `onTextLayout`) builds its TextKit 1 stack in one private `RCTTextLayoutManager` method, which makes that method the place to hook.
- **[iOS balancing alternatives](ios-balancing-alternatives.md):** ways to narrow lines without the two problems prototype 04 found. It recommended balancing after React Native's font scaling, and narrowing the text container rather than indenting the paragraph. It also pointed to a per-line `NSTextContainer` subclass as the route to minimum raggedness, which became the shipped mechanism.
- **[iOS isolation options](ios-isolation-options.md):** how to balance without touching React Native's own `Text`, either by a private signal to the swizzle or by subclassing React Native's paragraph classes into a separate component. It informed the own-component design (prototype 10), which was later dropped for the polyfill ([ADR 0001](../adr/0001-ios-polyfill-swizzle.md)). The notes on React Native's text caches and class wiring still hold.
- **[iOS break candidates and widths](ios-plan-inputs.md):** how to find where a line may break and how wide each piece is, so the balanced breaks agree with TextKit for every script. It recommended `CFStringTokenizer` line-break units and logical-order `CTRun` advances, checked against TextKit with one repair retry ([ADR 0004](../adr/0004-break-candidates-from-the-tokenizer.md)).
- **[Android `textBreakStrategy` re-render](android-text-break-strategy-rerender.md):** why switching an Android `Text` to `balanced` at runtime doesn't take effect. `ParagraphShadowNode::updateStateIfNeeded` returns early when the string is unchanged and never compares `paragraphAttributes`. Unfixed upstream as of 0.89.0-rc.1.

## Prototypes

Throwaway code that answered one question each. The four with a branch are kept as `prototype/*` branches on GitHub.

- **03, Android `balanced`** (no branch). Android's native `textBreakStrategy="balanced"` evens out every line rather than squeezing to one narrower width, so the library needs no Android code. It also found the runtime-switch bug: switching to `balanced` didn't re-apply until the `Text` was given a new `key`.
- **04, negative `tailIndent`** (no branch; the code was never committed). Swizzling React Native's private stack builder and narrowing lines with a negative `NSParagraphStyle.tailIndent` worked: measure, draw, hit-test and `onTextLayout` all agreed. It proved the hook and the `textBreakStrategy="balanced"` flag, which React Native already parses on iOS. Two problems ruled out `tailIndent`: a pressed span's highlight ran past the narrowed line to the box edge, and `adjustsFontSizeToFit` couldn't be supported. It used a max-width squeeze (binary search for the narrowest width that keeps the line count) at about 1ms per build.
- **06, exclusion paths** (`prototype/06-ios-exclusion-paths`). Narrowing with an `NSTextContainer.exclusionPaths` strip, applied after React Native's font scaling, fixed both of 04's problems. Alignment and RTL stayed correct, at about 1ms per build. It found a React Native bug that draws RTL press highlights in the wrong place.
- **08, minimum raggedness** (`prototype/08-ios-min-raggedness`). Chose breaks with a dynamic program that minimises line-width variance at the default line count, and imposed them with an `NSTextContainer` subclass that returns each line's width. It matched Android `balanced` line for line on the hard samples, balanced each paragraph separately, kept a long word whole where the squeeze split it, and cost 0.59ms median against the squeeze's 1.26ms ([ADR 0002](../adr/0002-minimum-raggedness.md), [ADR 0003](../adr/0003-per-line-text-container.md)).
- **10, own paragraph component** (`prototype/10-ios-own-paragraph-component`). A separate Fabric component built from subclasses of React Native's paragraph classes balanced with no swizzle and left React Native's `Text` untouched in 27 of 27 cases. It was dropped for the polyfill ([ADR 0001](../adr/0001-ios-polyfill-swizzle.md)). Its React Native range finding still holds: 0.84 declares `ParagraphShadowNode final`, and everything the library relies on, including the private method, is unchanged from 0.85 through 0.89.0-rc.1 and `main`.
- **14, break candidates and widths on device** (`prototype/14-ios-plan-inputs-on-device`). The tokenizer and `CTRun` widths from the research above gave 0 mismatches with TextKit over about 1,700 builds across Latin, hyphens, soft hyphens, Japanese, Chinese, Korean (both modes), Thai, Arabic with English and inline views. Only tabs and words wider than the box fell back. Release median 0.48ms, p90 1.40ms. It showed a cache was needed (see below) and found that React Native's measure cache ignores `lineBreakStrategy`, and that TextKit 1 ignores `pushOut` in React Native.

## Findings worth keeping

- **Why the break cache lives in the hook.** React Native caches measure and `onTextLayout` lines, but not draw, hit-test or rect lookups, so one mounted paragraph builds its stack about three times, with draw on the main thread. Only the hooked builder sees every build. The cache is keyed on everything the breaks depend on (the attributed string, width, line limit, font-fit settings), so it never needs invalidating, and a Dynamic Type change simply misses once. It cut mean overhead per build from 0.41ms to 0.17ms in the shipped build.
- **No exact TextKit oracle on iOS.** `-[NSAttributedString lineBreakBeforeIndex:withinRange:]` is macOS-only, and probing TextKit line by line costs tens of milliseconds. A delegate that vetoes every break and records it could act as one, but it relies on undocumented behaviour and wasn't needed.
- **TextKit 1 breaks at a soft hyphen** even with hyphenation off, and draws a visible hyphen there. React Native never turns automatic hyphenation on.
- **`push-out`.** The design originally cleared `pushOut` on balanced paragraphs and restored it on fallback. Because TextKit 1 ignores `pushOut` in React Native, the shipped library leaves `lineBreakStrategyIOS` alone.
- **A box that fits the balanced lines** was considered and left as a possible opt-in ([ADR 0007](../adr/0007-balanced-text-keeps-the-default-box-width.md)).
- **Balanced breaks equal to the default ones.** When the balanced breaks equal default wrapping's (the text is already as even as it gets), the paragraph is still laid out with narrowed lines, which clips each line's trailing space, so `onTextLayout` widths come out slightly lower. Keeping default wrapping in that case would make the output exactly default's and skip a layout. Not built.
